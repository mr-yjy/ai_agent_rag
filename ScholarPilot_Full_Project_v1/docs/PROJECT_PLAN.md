# 研索智航 ScholarPilot：完整参赛实施方案

## 1. 项目定位

### 1.1 赛题

- 主赛道：华为企业赛题三——科研场景下复杂学术查询的智能论文搜索与推荐；
- 兼报建议：开放命题、应用创意类、生成式大语言模型与智能体方向；
- 项目名称：研索智航——面向复杂学术查询的预算感知多策略论文检索智能体；
- 英文名称：ScholarPilot: A Budget-Aware Multi-Strategy Agent for
  Complex Academic Search。

### 1.2 一句话价值

把研究者自然语言描述的复杂文献需求，转换为可解释、可迭代、可评测的
论文搜索计划，在控制 API、Token 和时间成本的同时，提高相关论文集合
的精确率与召回率。

### 1.3 目标用户

- 需要进行开题和文献综述的研究生；
- 寻找细分方向论文集合的科研人员；
- 需要追踪方法、数据集、引文链或时间范围的研究团队；
- 需要能够复查检索过程，而不仅是得到一段生成式回答的用户。

## 2. 问题定义

普通检索引擎适合关键词搜索，但真实科研问题常常同时包含：

- 主题条件；
- 方法条件；
- 数据集或实验条件；
- 时间、会议或期刊条件；
- 必须满足和优先满足条件；
- 排除条件；
- 对权威性、时效性和多样性的不同偏好。

例如：

> 寻找 2024—2026 年使用查询分解或引文扩展进行复杂学术论文检索的
> LLM Agent 论文，优先包含公开代码和完整评测。

系统不应只把整句话交给一次搜索，而应显式解析约束、生成多条互补
查询、检索并扩展候选集、进行分阶段排序，最后输出带证据的论文集合。

## 3. 评分导向

赛题的自动评分重点是：

- F1 Score：70%；
- 运行效率：20%；
- 回复结果结构化：10%。

竞赛得分与专家评分还会考察创新性、落地可行性和泛化性。因此项目必须
避免“功能很多但 F1 无提升”的常见问题。

核心优化目标：

1. 先扩大候选集合，提高 Recall；
2. 再用约束判断和精排控制 False Positive，提高 Precision；
3. 使用缓存、级联模型和预算停止控制成本；
4. 所有输出都能定位到论文标题、摘要或元数据证据。

## 4. 总体架构

```text
用户问题
  ↓
Query Contract：主题、方法、时间、必须、偏好、排除
  ↓
Planner：关键词查询、语义扩展查询、引文扩展计划
  ↓
Retriever：OpenAlex + Semantic Scholar（第二阶段）
  ↓
Candidate Store：去重、缓存、来源追踪
  ↓
Fast Ranker：BM25 / Embedding
  ↓
Deep Ranker：Cross-Encoder / LLM Judge
  ↓
Verifier：证据覆盖与反事实一致性检查
  ↓
Budget Controller：继续搜索或停止
  ↓
结构化结果：论文、理由、证据、分组、关系图、成本
```

## 5. 数据结构

### 5.1 Query Contract

```json
{
  "topic": ["academic paper search"],
  "methods": ["query decomposition", "citation expansion"],
  "must_have": ["LLM agent"],
  "preferred": ["open source", "evaluation"],
  "exclude": ["survey only"],
  "year_from": 2024,
  "year_to": 2026,
  "top_k": 20
}
```

### 5.2 论文统一结构

```json
{
  "paper_id": "OpenAlex or Semantic Scholar ID",
  "doi": "optional DOI",
  "title": "paper title",
  "abstract": "paper abstract",
  "year": 2025,
  "authors": ["A", "B"],
  "venue": "ACL",
  "cited_by_count": 50,
  "references": ["paper id"],
  "open_access": true,
  "sources": ["openalex"],
  "retrieval_routes": ["semantic_expansion", "citation_forward"]
}
```

统一结构的意义是让不同数据源可以去重、融合和统一评测。

## 6. 算法方案

### 6.1 查询解析

MVP 使用规则和术语映射，保证无大模型时也可运行。正式版使用 LLM
生成结构化 JSON，并通过 Schema 校验。解析失败时回退到规则版本。

需要识别：

- 核心主题；
- 方法、模型、数据集、任务；
- 时间和发表源；
- 必须、偏好、排除；
- 用户更重视精确率还是召回率。

### 6.2 子查询生成

每个问题最多生成 3—5 条互补查询：

1. 原问题规范化查询；
2. 专业术语和同义词扩展查询；
3. 方法 × 任务组合查询；
4. 高相关种子论文的引文查询；
5. 查漏补缺查询。

不允许无限生成查询。每一条查询必须说明它预期补充哪一类候选论文。

### 6.3 多源召回

第一数据源使用 OpenAlex，第二阶段接入 Semantic Scholar。

召回路线：

- 关键词与字段搜索；
- Embedding 语义召回；
- 高相关论文参考文献扩展；
- 高相关论文被引论文扩展；
- 作者或研究主题扩展。

去重优先级：

1. DOI；
2. 学术图谱 ID；
3. 规范化标题；
4. 标题相似度加年份。

### 6.4 级联排序

第一阶段从数百篇中快速选出 Top-100：

- BM25；
- 双塔 Embedding；
- 年份和硬约束过滤。

第二阶段从 Top-100 选出 Top-30：

- Cross-Encoder；
- 约束覆盖特征；
- 标题和摘要证据。

第三阶段只处理边界候选：

- LLM 结构化判断；
- 反事实约束核验；
- 多样性重排。

建议总分：

```text
Score =
  λ1 × semantic_relevance
  + λ2 × constraint_coverage
  + λ3 × cross_encoder_score
  + λ4 × authority
  + λ5 × recency
  - λ6 × redundancy
```

所有 λ 必须在验证集上调整，不能凭主观感觉确定。

### 6.5 反事实证据核验

对 Top-20 或阈值附近论文执行：

1. 让模型判断论文是否满足原始约束，并输出摘要证据；
2. 替换一个核心约束形成反事实问题；
3. 比较判断变化；
4. 如果约束改变但判断几乎不变，降低该论文分数；
5. 如果找不到文本证据，标记为“相关但证据不足”。

该模块只作用于少量候选，避免大幅增加 Token 成本。

### 6.6 预算控制

系统维护：

- API 调用次数；
- 输入和输出 Token；
- 已用时间；
- 新增候选数量；
- 新增高相关候选数量；
- Top-K 排名稳定程度。

满足任一条件时停止：

- 连续两轮没有新增高相关论文；
- Top-K 排名变化低于阈值；
- 达到最大 API 或 Token 预算；
- 达到最大搜索轮数；
- 剩余查询路线预期收益低于成本。

## 7. 当前 Demo 边界

已实现：

- 规则查询解析；
- 中文术语到英文检索式映射；
- 多子查询；
- OpenAlex 服务端搜索；
- 内置数据自动降级；
- 候选去重；
- 透明五维排序；
- MMR 风格重复惩罚；
- 摘要证据提取；
- API、Token 估算、候选数和延迟统计；
- 响应式交互页面。

尚未实现：

- 大模型 Planner；
- Embedding 和 Cross-Encoder；
- 引文第二轮扩展；
- 反事实核验；
- 可学习停止策略；
- 人工标注测试集和 F1 计算。

## 8. 评测设计

### 8.1 数据集

优先使用：

- 赛题给出的 PaSa / RealScholarQuery；
- AstaBench 中 paper finding 任务；
- 团队自行构建的跨领域中文查询集。

建议自建 100 条查询：

- 计算机科学 35 条；
- 生物医学 20 条；
- 化学和材料 15 条；
- 金融和社会科学 15 条；
- 密码学和安全 15 条。

每条查询至少由两人独立标注相关论文，再处理分歧。

### 8.2 Baseline

- B0：原查询直接 OpenAlex；
- B1：一次 LLM 查询改写 + OpenAlex；
- B2：查询分解 + 多路召回；
- B3：B2 + Embedding；
- B4：B3 + Cross-Encoder；
- Full：B4 + 引文扩展 + 反事实核验 + 预算停止。

### 8.3 指标

```text
Precision = TP / (TP + FP)
Recall    = TP / (TP + FN)
F1        = 2 × Precision × Recall / (Precision + Recall)
```

同时记录：

- Recall@20、Recall@50；
- Precision@10、Precision@20；
- API 调用次数；
- 输入/输出 Token；
- 首次结果时间；
- 完整搜索时间；
- 每轮新增相关论文数量；
- 失败率和降级率。

### 8.4 消融实验

- 移除查询分解；
- 移除语义扩展；
- 移除引文扩展；
- 移除 Cross-Encoder；
- 移除反事实核验；
- 固定轮数替代预算停止；
- 不使用权威性和时效性特征。

## 9. 工程设计

### 9.1 模块

- `planner`：结构化查询与子查询；
- `providers`：OpenAlex、Semantic Scholar；
- `candidate_store`：去重、缓存、来源；
- `rankers`：BM25、Embedding、Cross-Encoder、LLM；
- `verifier`：证据和反事实；
- `controller`：预算和停止；
- `evaluation`：数据集、指标、消融；
- `web`：演示和结果导出。

### 9.2 可复现要求

- 配置文件记录模型、版本、参数和权重；
- 保存每个查询的检索日志；
- 缓存 API 原始响应；
- 固定训练随机种子；
- 实验输出包括配置哈希和代码版本；
- Prompt 文件单独管理；
- 公开测试集与开发集严格分离。

## 10. 安全与合规

- 不绕过学术 API 访问限制；
- 不抓取无授权全文；
- 显示数据来源和检索时间；
- 不生成不存在的 DOI、标题和作者；
- 生成式总结必须绑定论文证据；
- API Key 只放环境变量；
- 比赛材料详细标注数据、算法和代码来源。

## 11. 里程碑

### M0：稳定基线

- 查询解析；
- OpenAlex；
- 透明排序；
- 页面；
- 日志。

验收：任意 10 条查询均能返回结构化结果，接口失败可降级。

### M1：可评测语义检索

- 建立验证集；
- Embedding 召回；
- Precision、Recall、F1；
- Baseline 对比。

验收：结果可重复，并取得相对 B0 的稳定提升。

### M2：深度精排

- Cross-Encoder；
- 难负样本；
- 阈值优化；
- 多学科泛化。

验收：在 Recall 不明显下降时提高 Precision。

### M3：Agent 闭环

- 引文扩展；
- 反事实核验；
- 预算停止；
- 搜索轨迹。

验收：相对固定搜索轮数，在接近 F1 下减少调用和时间，或在接近成本下提高
F1。

### M4：参赛交付

- 项目文档；
- 300 字简介；
- 不超过 5 分钟视频；
- 代码和使用说明；
- 技术与实验附录；
- 匿名检查。

## 12. 风险

| 风险 | 影响 | 应对 |
| --- | --- | --- |
| API 限流或不稳定 | Demo 失败 | 缓存、重试、双源、内置降级 |
| 查询分解产生无效查询 | Recall 降低 | Schema、查询类型模板、验证集 |
| LLM 精排成本过高 | 效率失分 | 级联排序，只判断 Top-N |
| 引文扩展噪声过多 | Precision 降低 | 只从高置信种子扩展 |
| 只在 CS 上有效 | 泛化失分 | 跨学科验证集和分层报告 |
| 功能堆叠无指标提升 | 文档缺乏说服力 | 每个模块做消融实验 |
| 团队时间不足 | 无法提交 | 先保 M0/M1，再增加创新 |

## 13. 推荐团队分工

- 算法与评测：查询规划、排序、验证集、F1、消融；
- 检索与后端：API、缓存、日志、服务稳定性；
- 产品与材料：界面、图表、项目文档、视频和答辩。

如果只有两人，第一人负责算法和评测，第二人负责后端、界面和材料。

## 14. 初赛展示脚本

1. 展示传统关键词搜索对复杂条件的遗漏；
2. 输入一条包含主题、方法、年份和偏好的复杂查询；
3. 展示结构化 Query Contract；
4. 展示多个子查询和搜索轨迹；
5. 展示论文排名和摘要证据；
6. 展示调用数、Token 和时间；
7. 切换一个约束，展示排序变化；
8. 展示 Baseline 与完整系统的 F1 和成本对比；
9. 总结应用价值和后续扩展。
