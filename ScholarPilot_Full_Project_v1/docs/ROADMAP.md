## P0：解除 v0.6 发布阻塞

### 1. 凭据与 Git 历史

- 账户所有者确认曾进入历史的 DeepSeek/OpenAlex Key 已撤销并轮换；
- 仓库所有者批准历史重写、备份、强推窗口和协作者通知方案；
- 清理后重新运行当前树、完整历史和客户端构建物扫描，全部达到 0 命中；
- 建立可复核的 v0.6 基线提交。

历史重写会影响所有协作者，未获得明确授权前不执行。

### 2. 冻结可信评测集

- 人工处理当前 58 个 warning；
- 把旧式相关论文列表迁移为实体级别名分组；
- 至少冻结 30 条、3 个学科的 development/holdout 数据；
- 由第二位复核者处理争议与难例；
- 将 manifest 从 `annotation_required` 更新为 frozen 状态。

### 3. 质量和效率验收

- 运行直接检索、查询分解、多源召回、引文扩展、LLM 精排、反事实核验和预算停止
  的可复现消融；
- 保存 P@10/20、R@20/50、F1@20、P50/P95、API、LLM、Token 和逐查询结果；
- 相同配置、种子和缓存条件下至少复现两次；
- 在可信真实检索集确认 P50 ≤ 20 秒、P95 ≤ 45 秒；
- 不用未冻结数据或本地 mock 延迟替代正式结论。

## P1：Staging 与 Production

### 4. Staging

- 提供可访问的 Python HTTPS 服务和 Web staging；
- 完成 health、401、CORS、真实空结果、单源降级、全源失败、55 秒超时和取消验收；
- 执行 20 个 HTTP 并发请求，验证 requestId、指标隔离、429 和活动并发归零；
- 使用六类固定 fixture 完成真实浏览器视觉验收；
- 保存机器验收、负载、评测和密钥扫描报告。

### 5. Production

- 选择单实例部署，或先接入 Redis/平台级共享限流；
- 使用独立 production secrets 部署 staging 已验收的不可变版本；
- 完成 production smoke test、并发和客户端构建物扫描；
- 建立错误率、P95、429、上游降级率与活动并发监控；
- 验证回滚演练后再正式发布 v0.6.0。

部署细节见 [`DEPLOYMENT.md`](DEPLOYMENT.md)。

## P2：发布后的算法实验

这些能力当前均未实现，必须先通过受控实验再决定是否进入产品：

1. **Embedding 语义召回**：与关键词 baseline 比较 Recall、F1、延迟和成本；
2. **Cross-Encoder 精排**：只处理粗排候选，比较不同 Top-K 的收益；
3. **前向引文与多跳扩展**：严格限制种子、分支和总 API 预算；
4. **权重/阈值扫描工具**：仅在 development 集搜索，输出最佳配置和完整轨迹；
5. **学习型停止策略**：与当前可解释规则早停对比，不能降低可靠性和可观测性。

每项实验都应保留当前透明规则实现作为 baseline，一次只改变一个因素，不以个别
展示案例替代冻结集指标。
