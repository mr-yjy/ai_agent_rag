# ScholarPilot v0.6 超时根因与治理报告

## 结论

v0.5 的主要风险不是某一个固定慢函数，而是多个各自拥有完整超时和重试权的步骤
串联后，最坏耗时可以无上限叠加。v0.6 已把 live 链路改成共享的 50 秒 Python
截止时间，前端代理在 55 秒终止，并预留约 5 秒用于错误组装与网络传输。

## 根因

1. LLM、学术数据源、引文扩展和重试原来只看自己的单步超时，不知道请求还剩多少
   时间。
2. 查询分解、双源召回、引文扩展、迭代、精排和反事实验证可连续发生，单步都合法
   但总和可能超过前端边界。
3. `Retry-After` 或指数退避可能占用请求剩余时间，等待结束后仍继续发起下一步。
4. 引文扩展和第二轮过去更接近固定流程，没有先判断候选缺口和边际收益。
5. 浏览器取消只终止前端等待，Python 后续可选阶段仍可能继续消耗并发槽和配额。
6. 成功空集合与上游失败的语义不够清楚，空结果可能被错误包装为后端故障。

## 已实施控制

| 层级 | 控制 |
| --- | --- |
| 浏览器到前端 | `request.signal` 与 55 秒超时合并；取消返回结构化语义 |
| 前端到 Python | 传播取消；后端不可达、超时和协议错误使用稳定错误码 |
| Python 请求 | 一个 `SearchDeadline` 贯穿所有步骤，总预算默认 50 秒 |
| 单步骤 | 实际超时为 `min(请求值, 阶段上限, 剩余总预算)` |
| 重试 | 仅 429、可重试 5xx、网络瞬断；带抖动且不等待超预算退避 |
| 可选工作 | 预算不足时不启动引文扩展、迭代、精排或反事实验证；Selector 超时改用词法筛选 |
| 检索成本 | 初始子查询最多 3 条，总 API 默认最多 10 次，支持早停与熔断 |
| 可观测性 | 响应记录 `requestId`、`stageTimings`、`budgetRemainingMs` 和 `stopReason` |

## 验证证据

- 自动化测试覆盖：截止时间耗尽、阶段累计上限、客户端取消、取消后跳过精排、
  单源失败、全源失败、真实空集合，以及 `Retry-After` 超出预算时不等待不重试。
- 本地完整测试当前为 44/44；前端代理和渲染/API 测试为 3/3。
- demo 回归仅用于管线校验，P50/P95 约为 2/2 ms，不代表 live 网络延迟。

## 尚未完成的实测

计划要求的 30 条可信 live 查询 P50/P95 仍未生成。现有评测集有 58 个数据 warning，
且没有完成 staging 部署，所以不得用 demo 延迟或少量展示查询代替 live 指标。待
验证集冻结和 staging 可用后，应在相同配置、缓存状态和随机种子下连续运行两次，
确认 P50 不高于 20 秒、P95 不高于 45 秒，并保存最慢阶段和逐查询输出。
